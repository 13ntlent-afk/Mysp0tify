# Azure Deployment Log — Mysp0tify

This document records exactly what was provisioned in Azure for this project, the CLI commands used, why each one was run, and the order they were executed in. Use it as a reference for rebuilding, tearing down, or auditing the environment.

## Final Architecture

- **Resource Group:** `rg-spotify-web-demo` (Southeast Asia / East Asia)
- **Cosmos DB Account:** `cosmos-spotify-web-prod` (Serverless, SQL API)
  - **Database:** `cosmo-spotify-db`
  - **Container:** `subscription` (partition key `/email`)
- **Static Web App:** `spotify-web`
  - **Hostname:** `nice-pond-03e938600.7.azurestaticapps.net`
  - **Source:** GitHub repo `13ntlent-afk/Mysp0tify`, branch `main`
  - **API:** Managed Azure Functions in `/api`, deployed automatically alongside the static site
- **CI/CD:** GitHub Actions workflow auto-generated by Azure at `.github/workflows/azure-static-web-apps-nice-pond-03e938600.yml`

## Command Sequence and Rationale

### 1. Authenticate the CLI
```powershell
az login
```
Signs in to Azure and selects the subscription (`Azure subscription 1`) all subsequent commands operate against.

### 2. Create the first resource group
```powershell
az group create --name rg-spotify-web-prod --location southeastasia
```
Resource groups are the container for all related resources (Cosmos DB, Static Web App, etc.), so a group must exist before creating anything else. This first attempt used the `-prod` naming, later abandoned (see step 5).

### 3. Inspect existing Cosmos accounts
```powershell
az cosmosdb list --output table
az cosmosdb show --name spotify-web --query "..." --output table
```
Checked whether a Cosmos account already existed in the subscription before creating a new one, to avoid duplicating resources and to confirm which resource group an existing account belonged to (`show` requires `--resource-group` or `--ids`, which is why the first `show` call failed with "are required").

### 4. Attempt to list Cosmos SQL databases
```powershell
az cosmosdb sql database list --account-name spotify-web --resource-group <RG_FROM_ABOVE> --output table
```
Intended to enumerate databases inside the existing account. Failed locally because `<RG_FROM_ABOVE>` was a literal placeholder — PowerShell interpreted `<` as the redirection operator, which it does not support.

### 5. Delete the abandoned resource group
```powershell
az group delete --name rg-spotify-web-prod --yes --no-wait
```
Removed the first resource group (and everything in it) once it became clear a fresh, clearly-scoped demo environment was preferred over reusing the ambiguous existing `spotify-web` account. `--no-wait` avoids blocking the terminal on a slow delete.

### 6. Create the real resource group
```powershell
az group create --name rg-spotify-web-demo --location southeastasia
```
New home for every resource used by this deployment.

### 7. Attempt to create Cosmos DB with free tier
```powershell
az cosmosdb create --name cosmos-spotify-web-prod --resource-group rg-spotify-web-demo `
  --locations regionName=southeastasia failoverPriority=0 `
  --capabilities EnableServerless --enable-free-tier true
```
Tried to minimize cost using the one free-tier Cosmos account allowed per subscription. Failed because a free-tier account already existed elsewhere in the subscription (`BadRequest: Free tier has already been applied...`).

### 8. Create Cosmos DB (serverless, no free tier)
```powershell
az cosmosdb create --name cosmos-spotify-web-prod --resource-group rg-spotify-web-demo `
  --locations regionName=southeastasia failoverPriority=0 `
  --capabilities EnableServerless
```
Successfully created the Cosmos account. `EnableServerless` avoids provisioning fixed RU/s throughput, so cost is pay-per-request — appropriate for a low-traffic demo app instead of committing to autoscale/manual throughput.

### 9. Create the SQL database
```powershell
az cosmosdb sql database create --account-name cosmos-spotify-web-prod `
  --resource-group rg-spotify-web-demo --name cosmo-spotify-db
```
Creates the logical database (`cosmo-spotify-db`) inside the Cosmos account that the container will live in.

### 10. Create the container
```powershell
az cosmosdb sql container create --account-name cosmos-spotify-web-prod `
  --resource-group rg-spotify-web-demo --database-name cosmo-spotify-db `
  --name subscription --partition-key-path "/email"
```
Creates the `subscription` container used by [api/cosmos.js](api/cosmos.js) to store subscription documents. Partition key `/email` was chosen because lookups and de-duplication in [api/index.js](api/index.js) key off the subscriber's email address, giving even distribution and efficient point-reads.

### 11. Retrieve the primary key
```powershell
az cosmosdb keys list --name cosmos-spotify-web-prod `
  --resource-group rg-spotify-web-demo --query primaryMasterKey --output tsv
```
Fetches the master key needed by the API to authenticate against Cosmos DB (used as `COSMOS_KEY`). `--query`/`--output tsv` extract just the raw key value instead of the full JSON payload.

### 12. Confirm no Static Web App exists yet / find stale workflow
```powershell
az staticwebapp list --output table
```
Checked for an existing Static Web App before creating one, and confirmed no `spotify-web` SWA existed in the current subscription/resource group at that point — a leftover `.github/workflows` file from an earlier, deleted SWA attempt was removed from the repo so `az staticwebapp create` could generate a clean one.

### 13. Create the Static Web App, linked to GitHub
```powershell
az staticwebapp create --name spotify-web --resource-group rg-spotify-web-demo `
  --source https://github.com/13ntlent-afk/Mysp0tify --branch main `
  --login-with-github
```
Creates the Static Web App and, via `--login-with-github` (device-code OAuth flow), automatically:
- Registers the GitHub repo as the deployment source.
- Generates and commits a GitHub Actions workflow (`azure-static-web-apps-nice-pond-03e938600.yml`) to `main`.
- Adds the deployment API token as a repo secret (`AZURE_STATIC_WEB_APPS_API_TOKEN_NICE_POND_03E938600`) so the workflow can authenticate to Azure without manual secret handling.

### 14. Wire Cosmos credentials into the Static Web App's API
```powershell
az staticwebapp appsettings set --name spotify-web --resource-group rg-spotify-web-demo `
  --setting-names `
  COSMOS_ENDPOINT="https://cosmos-spotify-web-prod.documents.azure.com:443/" `
  COSMOS_KEY="<primary key from step 11>" `
  COSMOS_DATABASE="cosmo-spotify-db" `
  COSMOS_CONTAINER="subscription"
```
The managed Functions API in `/api` reads these as environment variables (see [api/cosmos.js](api/cosmos.js)) to connect to Cosmos DB. Application settings are the SWA equivalent of Azure Functions' app settings — they're injected at runtime and never committed to source control.

### 15. Verify configuration
```powershell
az staticwebapp appsettings list --name spotify-web --resource-group rg-spotify-web-demo -o json
```
Confirms the four settings above were actually persisted before relying on them.

### 16. Sync the auto-generated workflow locally
```powershell
git fetch origin main
git pull origin main
```
Azure's `--login-with-github` step pushed the new workflow file directly to `origin/main`; pulling brings that commit into the local clone so `git status` stays accurate.

## Post-deployment verification

- `GET https://nice-pond-03e938600.7.azurestaticapps.net` → `200 OK` (static site is served).
- `POST https://nice-pond-03e938600.7.azurestaticapps.net/api/subscriptions` with an empty body → `400` (validation error, not a routing/connection failure), confirming the managed Functions API and its Cosmos DB wiring are live end-to-end.

## Notes / gotchas

- Free tier is a **per-subscription** limit (one account), not per-resource-group — reuse existing free-tier accounts where possible instead of trying to create a second one.
- PowerShell treats `<` and `>` as redirection operators; never leave placeholder tokens like `<RG_FROM_ABOVE>` literally in a command — substitute the real value.
- `az cosmosdb show` (and similar `show` commands) require either `--resource-group` or `--ids`; the resource name alone is not enough to disambiguate.
- Deleting a resource group with `--no-wait` returns immediately; the delete continues in the background.
- `api/list-subscriptions.js` is a **local developer utility** (run with `node list-subscriptions.js`) for inspecting Cosmos data directly — it is not an HTTP-exposed API route, unlike `subscriptions` defined in [api/index.js](api/index.js).
